# The Encounter Presenter owns the engine and hands the screen snapshots

All GUI code is game-side, under `ui/`, and only one object in it touches the rules engine. The Encounter Presenter (`ui/encounter/encounter_presenter.gd`) owns the `MmEngine` and the `MmEncounterDriver`. After every change it hands the Encounter Screen a snapshot: the Hero's Player View, the Pending Decision the Hero must answer (or none), whether the Villain is thinking, whether the Hero is holding priority, whether anything can be undone, the Event Log entries added since the previous snapshot, and a `CardLook` for every Game Object the view shows. The screen draws from the snapshot and nothing else. A test scans `ui/` and `tools/` and fails if any file but the presenter mentions `MmEngine`, `MmGameState`, `MmEncounterDriver` or `game_state(`. This is ADR 0005's boundary carried into the GUI: the screen cannot show the Hero a card they may not see, because it is never handed one.

**The worker thread.** A Normal AI decision can take over a second (ADR 0020), so the Villain's Agent never runs on the main thread. The presenter runs `driver.run()` on a `WorkerThreadPool` task with `decision_cap = 1`, so each task gives exactly one Villain answer and the screen is told after every one (A238). While a task runs, the worker is changing the game, so the main thread must not read the engine at all. The presenter therefore makes the snapshot *before* it starts the task, flags that snapshot as "the Villain is thinking", and refuses every command until the task has been collected. Conceding is the one exception: it waits for the thought already begun, then ends the encounter without playing anything more. A redraw in the middle of a thought, such as when the window is resized, uses the snapshot it already has. The prototype got this order wrong once and built a Player View while the worker was recalculating layers, which crashed on a half-computed permanent; that is the failure this rule prevents. Leaving the screen waits for a running task first.

**Art.** A Player View names a card by its Card Identity. `MmEngine.run_card(card_id)` leads from that back to the Run Card, and the presenter takes the art key from its Card Definition's file name. An ability on the stack takes its source's art. The alternative, rebuilding the engine's numbering from the setup's deck order inside the GUI, would have copied an engine rule and broken silently if it changed (A241).

**Events.** A snapshot carries only the events since the one before. Pacing reads them to decide how long the snapshot stays up (ADR 0027). A rewind (undo, or canceling a cast) only shortens the log, so it hands out nothing and is never animated (ADR 0015); the snapshot says that it came from one.

**Passing for the Hero.** The presenter passes priority on the Hero's behalf in three cases, all decided from the Hero's Player View alone. Only priority is ever passed: choosing attackers or blockers, ordering triggers, discarding and every other decision is the Hero's to answer.

- *Auto-pass*, the standing setting, on by default. The Hero is asked only on a step that has a stop and where they could cast, play or activate something other than a mana ability, or when the Villain's spell or ability is on top of the stack. Each player's turn has its own row of stops, held in `StepStops`; untap and cleanup never hold one. Clearing the stop the Hero is waiting at lets auto-pass carry on at once. It is turned on and off on the Pause Menu's settings page and kept in the settings file with the Game Speed. It used to be a box on the Hero's panel; it moved because it is set once and left, and that place was wanted for the Yield.
- *A Yield*, set with the Yield Turn box on the Hero's panel. Every priority of the turn is passed, whatever the stops say, with auto-pass on or off, and with the Villain's spell or ability on the stack too: a Yield that stopped for each thing the Villain did would not be the Hero saying "I have nothing this turn". It can be set at any moment, the Villain's thinking included, when it is for the turn the game is in once they are done. Setting it while the Hero has priority passes at once. It ends by itself when the next turn begins, so a box left checked can never pass through a turn the Hero did not mean to give up, and every encounter starts without one.
- *The Hero's own spell or ability on top of the stack* is passed whether auto-pass is on or not.

**The Hold Key (Ctrl) stops all three.** While it is down, a pass that is due is not made, and the Hero has priority instead, in a step with no stop as much as any other: it is the one way to act where auto-pass or a Yield would have gone by, without turning either off. A priority kept this way is latched until the Hero's next answer, so letting go of the key does not pass; with a live key the Hero would have to hold it down while clicking a card, its targets and its mana, and a slip would pass the priority they stopped for. The key is read at the moment the pass would be made, and again for each one after it. Neither setting is changed by it: a Yield carries on from the Hero's answer.

Changing auto-pass, a stop or the Yield looks at the pending decision again, except while the Villain is thinking, when it applies from the next decision, and under the Pause Menu, when it waits for the game to resume.

**Pacing.** The presenter holds back collecting the Villain's next answer until the Hero has had time to read the last one: 500 ms after an action and 270 ms after tapping for mana at the Fast Game Speed (ADR 0027), with thinking time counted toward the wait (A238, A358). A step of the turn is shown for at least 100 ms before the game leaves it, which also puts off a pass auto-pass makes for the Hero. ADR 0027 has the rule and the reasons, along with how the screen is animated.

**The screen.** `EncounterLayout` works out every Region's rectangle from the screen's size, so "no two Regions overlap" is tested without a window. The game is designed at 1920 × 1080 and stretched with `canvas_items` and the `expand` aspect: rows keep their share of the height, the sidebar and the pile column keep their width, and extra width goes to the battlefield (A205). The six piles fill the right column with equal spacing, the Villain's above the Hero's and mirroring them: the Hero's run library, graveyard, exile from the top and the Villain's exile, graveyard, library, so the two libraries meet in the middle (A294). The Hero's controls (undo, pass and Yield Turn) fill a section of the Hero's panel in the sidebar, under the Emblems button, and the Villain's panel says "The Villain is thinking…" in the same place. The Hero's hand sits a quarter of a card below the bottom of the screen, cut off a little under its type lines. The Hold Panel takes the left end of the Villain's hand's strip, at the top, and the Villain's hand keeps to the middle between the same bounds as the Hero's. The Info Panel takes the left end of the hand's strip, and the hand keeps to the middle of the battlefield between strict bounds, as far in from the right as the Info Panel reaches from the left, squeezing evenly as it grows, so it can never overlap the panel however many cards it holds. Lands of one name stand together in their row: a new land goes just right of the rightmost land with its name. The Hero's rows sit that much lower with it while the Villain's stay up by their hand, which opens a 90 px lane across the middle of the board for combat. A player's nonland row is two lines: creatures toward the left and middle, and other permanents to their right at 85% of the size, set back toward that player's edge and taking at most a third of the row (A276, A277). A line keeps its faces' size and scrolls sideways when it overflows, with an arrow at each end it can scroll toward and a thin bar beneath; land rows shrink their faces instead (A278). Once attackers are declared, creatures not in the combat are drawn a fifth smaller, and attackers and blockers step 40 px toward the middle, into the lane between the two players' rows (A279). The stack is not a Region. It is the Stack Window, which is there exactly while something is on the stack. Every zone's window shares one shell, `ZoneWindow`: draggable and resizable within the battlefield, scrolling on overflow, titled with the zone's name and count, keeping its place and size while hidden, and closable except for the Stack Window.

**Decisions get their own inputs, one kind at a time (A243).** Choosing from a list is not fun, so every decision kind will have an input of its own: glowing targets to click, mana sources to tap, cards to drag. Until a kind has one, the Debug Decision Panel answers it through one of its generic forms (`DebugDecisionForm`). There were five; pair up and split a number went with the combat decisions in 13c-2, and put in order went with ordering triggers in 13d-1, which leaves pick one and pick some. Casting and playing a land went to the hand in 13e-1, and the last four kinds went in 13e-2 (ADR 0030), when the panel and its forms were deleted. Every kind the engine can ask is now listed in `DecisionInputs` beside what answers it, and a test fails when the engine gains a kind that is not listed; a decision that somehow has no input shows what the engine asks in the Info Panel and raises an error, where before it would have fallen through to the panel. A kind was not finished until its panel form was deleted. The Glow marks what a decision can choose (orange-red for targets, blue for mana sources, gold for attackers and blockers to choose, purple for abilities to activate, green otherwise; two of them, split, on something that offers two kinds of thing), and is drawn from the same map that says what a click answers (ADR 0022). A Glow, and any other effect on a thing's border, is a child of the Control it marks, so it turns and resizes with it. Activating a permanent's ability, paying mana, choosing a target, declaring attackers and blockers, and dividing combat damage have their own inputs since 13c, and their forms are gone.

**What a redraw costs, and what is kept.** The board (every face, row, pile and the hand) is thrown away and rebuilt from each snapshot, which keeps it a function of the snapshot alone. That is cheap: a face takes 0.1 to 0.2 ms to build, and a mid-game board about 7 ms. It was 44 ms until it was measured, and almost none of that was faces. A third was the arrows of the four scrolling lines, whose "◀" and "▶" are not in the game's font: Godot lays out a character from a fallback font in about a millisecond, several times for each button built or restyled. A third was the two player panels, built afresh with thirty-odd buttons each, two of them carrying such a character. So the arrows are drawn as triangles and painted only when their color changes, and the player panels are the one part of the screen that is built once and then updated: `PlayerPanel.show_snapshot()` still draws from the snapshot and nothing else, but changes only what shows differently.

Two alternatives were rejected. Letting each screen node read the engine directly is simpler to write, but it is how the crash above happened, and it makes "what may the Hero see" a property of every node instead of one object. Running the whole Villain turn in a single task would save a few thread handoffs, but the screen would only see where the turn ended up, with nothing to draw in between.
